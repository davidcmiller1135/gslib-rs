## D-003: Where the oracle runs
- Status: decided
- Topic: harness.md
- Question: Should GSLIB run in CI, or offline with committed fixtures?
- Options: committed fixtures plus a pinned recipe; build GSLIB in every CI
  run; committed fixtures plus a scheduled regeneration job.
- Decision: **committed fixtures plus a pinned recipe.** (The recipe's
  location, originally `tools/oracle/`, is superseded by D-008: a Rust
  `xtask`.)
  The recipe downloads GSLIB, verifies a pinned checksum, applies output-format
  widening, builds with double promotion, runs the reference cases, and writes
  fixtures with provenance. Tests compare only against committed fixtures. A
  scheduled regeneration job may be added later.
- Rationale: CI stays fast, offline and deterministic (`AGENTS.md`, *Deterministic
  and isolated*); provenance is explicit; GSLIB source is never committed
  (D-002).
- Consequences:
  - Format widening is done by generic rewrite rules in the recipe, not by
    patch files, because patch hunks contain GSLIB source lines (D-002).
  - Committing GSLIB-computed *outputs* still needs the licence check in D-002
    before the first fixture lands.
  - The recipe needs gfortran wherever it runs, plus network access to
    gslib.com (blocked in this session's environment today).

## D-004: Input data for reference cases
- Status: decided
- Topic: harness.md
- Question: Synthetic data, the GSLIB book's data sets, or both?
- Options: synthetic only; book data sets only; both.
- Decision: **both.** Synthetic suites, generated by a seeded script committed
  here, target specific behaviours and edge cases (ties, duplicate locations,
  missing values, anisotropy, degenerate inputs). Book data sets serve as
  realism checks.
- Rationale: synthetic data is ours to redistribute and can isolate each
  behaviour; book data sets are what GSLIB users actually run.
- Consequences: book data sets may be committed only once their licence is
  known (D-002). Every synthetic case documents what it exercises.

## D-007: How a case's configuration is shared between Fortran and Rust
- Status: decided
- Topic: harness.md
- Question: GSLIB's own .par as truth, our own case schema, or parameters
  transcribed into tests?
- Options: `.par` as the source of truth with a per-program reader; our own
  case schema with a generated `.par`; hand transcription.
- Decision: **our own case schema.** Each reference case is a TOML file. The
  recipe generates GSLIB's `.par` from it, and Rust tests read the same TOML.
- Rationale: user's choice. The schema is ours, so it can be versioned,
  validated and documented independently of GSLIB's positional layouts.
- Consequences:
  - The recipe needs a `.par` generator per program. Each layout must come
    from the source (`TODO(parity-verify)` until the archive arrives).
  - The generated `.par` is stored with each fixture, for provenance.
  - A user-facing `.par` reader (roadmap step 8) stays a separate, later item.
  - The schema carries a version number. Parsing it in tests needs a TOML
    dependency (to pass `cargo deny`, dev-only where possible).

## D-008: Recipe language and schema location
- Status: decided
- Topic: harness.md
- Question: Where is the case schema defined, and what language is the
  recipe written in?
- Options: Rust xtask crate; Python script; shell with templates.
- Decision: **Rust `xtask`**, invoked as `cargo xtask oracle --archive PATH
  ...`. Rust types define the schema once, and both the recipe and the tests
  use them. Shell is used only to invoke gfortran.
- Rationale: one language and one schema definition, so the recipe and tests
  cannot drift apart; the same strict lints apply (`AGENTS.md`, *Rust & Repo
  Discipline*).
- Consequences (layout, to avoid dependency cycles):
  - `oracle-case`: an internal library crate (`publish = false`) with the
    schema types and TOML parsing;
  - `xtask`: a binary (`publish = false`) for build, `.par` generation, runs
    and fixture writing; depends on `oracle-case`;
  - `harness`: a tests-only crate (`publish = false`) depending on `gslib_rs`
    and `oracle-case`;
  - a `cargo xtask` alias in `.cargo/config.toml`.

  None of these is a dependency of `gslib_rs`, so the library stays lean.

## D-009: Fixture storage
- Status: decided
- Topic: harness.md
- Question: How is each fixture stored on disk?
- Options: verbatim GSLIB outputs plus provenance; a normalised format; both.
- Decision: **verbatim outputs plus provenance**, one directory per case:
  `tests/fixtures/gslib/<program>/<case>/` containing:
  - `case.toml`;
  - the input files;
  - the generated `params.par`;
  - GSLIB's output files exactly as written;
  - `provenance.toml`.
- Rationale: the stored output is the evidence. Interpreting it is the job of
  the Rust-side readers, so a reader bug cannot corrupt the reference
  (`AGENTS.md`, *No fabricated provenance*).
- Consequences: the harness needs readers for each output format: GeoEAS
  through `io::parse_gslib`, plus small readers for formats like `gamv`'s.
  `provenance.toml` records:
  - archive SHA-256;
  - gfortran version and full flags;
  - rewrite-rules version;
  - case-file SHA-256;
  - recipe (repository) commit;
  - generation date (UTC);
  - command line.

## D-010: Comparing deterministic outputs
- Status: decided
- Topic: harness.md
- Question: What does "matches" mean for a deterministic program?
- Options: per-quantity tolerances with justifications; one global tolerance;
  ULP-based comparison.
- Decision: **per-quantity tolerances, each justified:**
  - structure must match exactly: row and column counts, variable names, and
    which entries are missing/UNEST;
  - direct formulas (variogram values, transforms, model evaluation) default
    to a relative error of 1e-12;
  - linear-solve results (kriging estimates and variances) are bounded by
    k · cond(A) · ε, with the harness computing cond(A) of each system;
  - a case may override a default only with a written justification in
    `case.toml`;
  - failures report the maximum absolute and relative error and their
    location.
- Rationale: tolerances reflect where the error comes from (`AGENTS.md`,
  *Differential and fixture tests*). A single global value would hide
  regressions in exact formulas or flag well-understood solver differences.
- Consequences: 1e-12 and the constant k are **initial values**, to be
  calibrated on the first fixtures and fixed by a new decision entry. Never
  loosen them quietly (`AGENTS.md`, *Never weaken … to get green*). The
  harness needs a condition-number estimate (e.g. from nalgebra's SVD).

## D-011: Statistical parity for stochastic programs
- Status: decided
- Topic: harness.md
- Question: How is statistical parity judged for `sgsim`, `sisim`, `sasim`?
- Options: ensemble vs ensemble; each implementation vs the model;
  two-sample distribution tests (KS/AD).
- Decision: **ensemble vs ensemble, plus independent invariants:**
  - GSLIB and gslib-rs each generate N realizations of the same case (N = 100
    on a small grid to start);
  - compared: ensemble means of the experimental variogram per lag, histogram
    quantiles, and data reproduction at conditioning nodes;
  - each difference in means must be within 5 standard errors, estimated
    from both ensembles;
  - separately, gslib-rs ensembles must reproduce the input model and
    histogram, so agreement with GSLIB is never the only check.
- Rationale: compares behaviour without needing identical random streams
  (`AGENTS.md`, *Parity levels*, *Statistical tests*).
- Consequences:
  - Fixed seeds make every outcome exactly reproducible, never flaky.
  - With about 50 comparisons per case at 5σ (≈ 5.7e-7 two-sided each, if
    near-normal), the chance of a false failure per case is about 3e-5.
  - N and the grid size set fixture size. Keep each stochastic fixture under
    ~2 MB; a larger fixture needs a decision entry.

## D-013: Honouring the GSLIB 2.0 notice; vendoring the source
- Status: decided
- Topic: harness.md (licensing affects the whole repository)
- Question: How do we honour the Stanford notice, and what may be committed?
- Options: MIT plus a NOTICE, with data sets and patches committable; MIT
  plus a NOTICE, committing nothing; also vendor the source.
- Decision: **vendor the source.**
  - Our own code stays MIT.
  - A top-level `NOTICE` reproduces the Stanford copyright and notice
    verbatim, and states that parts of gslib-rs are derived from GSLIB 2.0.
  - The GSLIB 2.0 archive, minus `BIN/` (executables, D-005), is committed
    byte-for-byte under `vendor/gslib-2.0/src/`, with `MANIFEST.sha256` and a
    provenance README.
- Rationale: user's choice. With the source in the repository the recipe is
  self-contained: no upload, no network, nothing to lose. Vendoring is
  permitted by the notice as long as it stays intact.
- Consequences:
  - **Vendored files are never modified.** `.gitattributes` disables line-ending
    conversion (they are CRLF), and the manifest verifies them. Build-time
    changes (format widening) are applied to a copy by the recipe.
  - The recipe reads `vendor/gslib-2.0/src/`. D-006's uploaded archive is no
    longer needed day to day, and `--archive` becomes optional (to re-verify
    against an original zip).
  - Book data sets (`DATA/`) can be used in fixtures directly (D-004).
  - Supersedes the "commit nothing from GSLIB" consequences of D-002 and D-003.
  - The provenance-ledger items (`docs/ROADMAP.md` §6) can now be checked
    against the vendored source.
